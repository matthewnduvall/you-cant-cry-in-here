# AGENTS.md — Project Context & Rules for "You Can't Cry in Here"

> **Note for coding agents (Claude Code, etc.):** This file contains the complete product, design, architectural, and domain context for *You Can't Cry in Here*. Always follow these rules and target the specific modular files listed in Section 2 when making edits.

---

## 1. Project Overview & Tech Stack
* **App Name:** *You Can't Cry in Here*
* **Framework:** Next.js 16.4+ (App Router, Turbopack, `cacheComponents: true` & `partialPrefetching: true` enabled in `next.config.mjs`).
* **Hosting & Backend:**
  * **Frontend Hosting:** Vercel (linked to GitHub repo `matthewnduvall/you-cant-cry-in-here`).
  * **Database & Auth:** Supabase (`supabase_schema.sql` in repo root defines `user_profiles`, `workout_history`, `routines`, `friendships`, `friend_invites`, and `shared_sessions` with Row-Level Security, plus the friendship functions/triggers; safe to re-run). One-time data migrations live in `supabase/migrations/`.
  * **Local Persistence:** Update-resilient `localStorage` engine (`yccih_app_state_v3`, Schema Version 3) with debounced 300ms auto-save and `.json` backup export/import.

## 2. Modular File Architecture (Read/Edit Only the Target File)
To keep agent edits fast and focused, views and state hooks are split into dedicated files:

* **App Shell & Header:**
  * `app/page.js` — Top-level state wiring, view router, and modal mounts (~900 lines).
  * `app/components/AppHeaderAndDrawer.jsx` — Sticky top navigation bar (Menu `☰`, title, `FEEDBACK` button; in the session/routine editor also `SessionTitleBar` — session name + green `SAVE` + red `RESET` — and `SessionRestTimerBar` flush beneath it; the header action cells and the rest bar ✓ share `SESSION_ACTION_COL` (58 px) so the orange NEXT bar ends exactly under the SAVE | RESET divider) and slide-out Hamburger Drawer. Header: an orange `←` BACK button just right of ☰ (not on Home), and the app title `YOU CAN'T CRY IN HERE` in the centre ("HERE" in orange): a button to Home on every page. The page's name (`PAGE_TITLES`: PERFORMANCE, STIMULUS, SOCIAL, CONFIGURATION, INFO, PROFILE, SESSION…) is not in the header: `PageTitle` (same file, 28 px) shows it at the top of the page itself, under the locked header (`page.js`, every view but Home). BACK = `handleBack` / `goBack` in `page.js`: a real back stack (`backStackRef`) of the places visited since Home (cleared on Home) — a place is a page, plus on the PROGRESS page its tab and a History workout opened from elsewhere (`openHistoryWorkout`, e.g. a chart point, is its own step, so BACK returns to the chart); tab switches on one page are not steps. Each step is also a browser history entry (`pushState` with its depth in `state.yccihBack`, counted in `browserDepthRef`, capped at 30 because browsers keep only ~50 entries), and `popstate` runs the same `goBack`, so the phone's / browser's back gesture matches the ← (`ignorePopsRef` keeps the two in step when places are skipped). A popstate to a deeper entry (browser **forward**) is undone, never treated as back. Reaching Home (by any route) rewinds the browser to where the app started (`rewindToHome`), so back on Home leaves the app instead of stepping through dead entries. Skipped: pages that can't be shown any more (an editor without its draft, a friend profile without a friend, sign-in while signed in, a deleted History workout); empty stack = Home. The menu starts with `PROFILE (@user)` (with the profile photo) / `SIGN IN`, then `HOME`, `PERFORMANCE`, `STIMULUS`, `SOCIAL`, `CONFIGURATION`, `INFO`; signed out its footer reads `NOT SIGNED IN: SAVED ON THIS DEVICE ONLY`; signed in, a red `SIGN OUT` sits at the bottom under `LOGGED IN: <email>` (`onSignOut`). Signed out: a slim grey line under the header (`Not signed in: saved on this device only.` + orange `SIGN IN` + `JOIN`), hidden in the session / routine editor and on the sign-in page.
* **Custom State & Domain Hooks (`app/hooks/`):**
  * `app/hooks/useCloudAndStorageSync.js` — `localStorage` hydration, password recovery hash & email invite URL param detection (`?invite_from=...&beta_code=imnotcrying`), Supabase cloud pull/push, automatic invite-to-friend resolution, and `.json` backup export/import/reset.
  * `app/hooks/useWorkoutMutations.js` — Workout/slot/set creation, auto workout generation (`handleAutoBuildWorkout` for AUTO SESSION, `handleAddAutoSlot` for `+ ADD EXERCISE`), routine loading, drag-and-drop reordering, weight recalculation, saving, and deleting.
  * `app/hooks/usePlateCalculator.js` — Plate & Weight Calculator modal state (plates only; no DIRECT TOTAL mode — tap `TOTAL WEIGHT ✎` to type a number, which re-splits into plates). TOTAL WEIGHT always = bar + plates (× 2 for two sides) + `calcExtraLbs`: the part plates can't make up (e.g. 151.25 lb = 45 + 2 × 52.5 + 1.25) shows as a grey `+1.25 LB OTHER ✕` chip and stays when plates are added or removed, so the total never jumps. A set with no weight opens on the empty bar. Loads (`getLoadSetup`): barbell / trap bar / Smith = 45 lb bar + plates per side; EZ bar = 17 lb bar + plates per side; plate-loaded Lever / Sled = plates per side, no bar; dumbbell, kettlebell, cable / selectorized / machine stacks, landmine and everything else = the picked weights are the total (no bar, no ×2) and handlers for set weights, Personal Records (with optional `prRecordDate` that logs an individual History entry), and custom goal weights.
  * `app/hooks/useSessionSync.js` — Live session sync with a friend: invites (polled every 10 s), accept/decline, pulling the partner's structure every 3 s while synced, pushing own structural edits 0.7 s after they happen (latest edit wins, compared by `updated_at`), each athlete's numbers per set (`structure.values`, see G) with `editPartnerValues` / `partnerValues` for the friend's tab, and ending the sync on UNSYNC / RESET / save. The shared session is marked by `activeSession.syncId` (+ `syncPartnerId`, `syncPartnerName`).
  * `app/hooks/useIdleAutoFinish.js` — 15 minutes without a touch, click or key press (`yccih_last_activity_v1` in localStorage, so a closed or suspended app is checked when it returns; checked every 30 s and on returning to the foreground): a live session with at least one completed set is saved to History as it is (`handleAutoFinishActiveSession` in `useWorkoutMutations`: private, not a routine, `autoFinished: true`), closed, and a `SESSION SAVED` notice is shown. A session with nothing completed is left open.
  * `app/hooks/useAppUpdateCheck.js` — keeps open apps on the latest deployment (an iPhone home-screen app left running keeps its old code otherwise, and two synced phones on different versions don't sync numbers). Compares the build baked into the page (`process.env.APP_BUILD_ID`, set in `next.config.mjs` `env` from `VERCEL_GIT_COMMIT_SHA`) with `GET /api/version` (`app/api/version/route.js`, no-store): on returning to the foreground an older build reloads at once (state is already saved on the device); while in use (checks every 5 min and when back online) it shows `UpdateBanner` (`app/components/UpdateBanner.jsx`: `A new version of the app is ready…` + orange `RELOAD`) under the header.
  * `app/hooks/useTelemetryAndAnalytics.js` — Computes `effectiveOneRepMaxes` (highest calculated 1RM from History + manual overrides), `muscleStimulusStatus`, and `progressionSeriesByLift`. `buildProgressionSeriesByLift(history)` is exported (also used for a friend's chart).
  * `app/hooks/usePointerReorder.js` — Drag-to-reorder with pointer events (works with touch, unlike HTML5 drag-and-drop): `handleProps(key)` on each row's `DragNumberBadge` (which passes extra props through), the row attribute on each row, and `rowDragStyle(key)` in each row's style — the held row lifts and follows the finger (translateY + shadow + orange outline) and the landing row gets an orange `outline` (not an inset box-shadow, which the row's own filled cells cover); dragging back over the row's own place cancels the move; **not too sensitive**: the row only lifts after the finger moves 10 px (`LIFT_THRESHOLD_PX`) and only lands on another row once the finger passes that row's middle; rows are found by element within the held row's own list (keys like `0:0` repeat in every exercise, so never `querySelector` by key), and the latest drag state is kept in a ref so release never uses a stale position; options `attribute` (separate ones for nested lists), `canDrop`, and `edgeTop` / `edgeBottom` (holding near the screen edge auto-scrolls on a 16 ms timer, so rows can be dragged past off-screen ones; `edgeTop` clears the sticky session header). Used by ROUTINE PREFERENCES (`data-reorder-index`), exercises in `RoutineEditorView` (`data-slot-reorder`, handle props passed to SlotEditor as `dragHandleProps`) and sets in `SlotEditor` (`data-set-reorder="exIdx:setIdx"`; superset sets only move within their own exercise). No HTML5 drag-and-drop anywhere (it doesn't work with touch).

## 3. Critical Next.js 16 & Environment Rules
1. **No Unstable `Date.now()` in Client Prerender:** Because Next.js 16 `cacheComponents` is enabled, **never** call `Date.now()` directly inside a `useMemo` or top-level render body of a `'use client'` component. Always read `Date.now()` inside a `useEffect` (e.g., `stimulusNowMs`) or event handler.
2. **Verifying Changes:** Run `npm run lint` after edits. `npm run build` is the full check (it surfaces prerender errors like the `Date.now()` rule above). If a sandboxed terminal blocks Turbopack worker sockets on Windows, ask the user to run the command in their own PowerShell window instead.

## 4. Visual & UI Design System ("Crying": black ground, graphite tiles, one red)
The full design language is the project skill `.claude/skills/crying-interface-design/SKILL.md` (modelled on camera menus: a black screen, a few graphite tiles, quiet grey caps labels, large light numerals and a single red accent). Read it before building or restyling UI. Tokens live in `app/styles/kineticTokens.js` (`CRY`, CSS variables in `KINETIC_CSS`, and the `UI` style objects); shared controls in `Controls.jsx` / `Primitives.jsx` already follow it, so use them instead of hand-styling. **Colour words elsewhere in this file (orange, green, yellow, purple, "orange fill", "green SAVE", square corners, 20 px section titles…) describe the earlier Kinetic Brutalist look; where they disagree with this section, this section wins** (orange → white / selected or red where it is the screen's one action, green → white, yellow → grey, purple → grey).
* **Colour tokens (no other hues):**
  * Ground `#000000` (`--dp-color-ground`); tiles / list groups / secondary buttons `#1C1C1C` (`CRY.tile`, `--cr-tile`); a control inside a tile `#2A2A2A` (`--cr-tile-raised`); dividers `#2E2E2E` (`--dp-color-rule` = `--cr-hairline`); pill / dashed outlines `#3A3A3A` (`--cr-outline`).
  * Text: values / titles `#FFFFFF`; info lines `#BDBDBD`; caps labels, units, subtitles `#9A9A9A`; done / inactive / footers `#8A8A8A`.
  * **Red:** `#E20612` (`--cr-red`) is a **fill only**, with white text: the screen's one primary action or selected row. `#FF4A3D` (`--cr-red-text`) is red as **text** on black or graphite (destructive actions, warnings, overdue).
  * `--dp-color-accent` is **white**: "selected / actionable" is a white fill with black text (active pill, selected toggle, chosen row), never orange.
  * Exceptions kept on purpose: band colours (`BAND_COLOR_HEX`, the physical band's colour) and the invite email (`app/api/invite/route.js`).
* **One red thing per component** (changed from per screen): each component — a tile or card, a list group, a header bar, a pop-up — has at most one red element (a red fill, a linked chart-line + row pair, or one red text). A screen can show several. Current owners: the locked session header = `FINISH` / `SAVE` (RESET is red text in the same bar — treat the bar's FINISH | RESET pair as its action group); each **exercise card** = its **title** (exercise name in `--cr-red-text`; so the card's DELETE is grey and its other values white); a **blank live session** = `+ ADD EXERCISE` (LOAD ROUTINE dashed; FINISH appears with the first exercise); each **Personal Records row** = the exercise name; each **History row** = the session name (its ✕ is grey; it still asks); each **leaderboard** = the **#1 athlete's name** (everyone else white); Social friend / request / sent lists have no red (their ✕s are grey); the session name pop-up = SAVE NAME; Home's action row = NEW / CURRENT SESSION (AUTO SESSION is graphite); Sign in = `SIGN IN` (CREATE ACCOUNT is white); Configuration = `NEXT`; Performance chart tile = the highlighted lift (line + its row); Stimulus map = OVERDUE; Social = `SIGN IN` (signed out) or `SEND INVITE`; routine browser = `AUTO ROUTINE`; each pop-up = its confirm button; Info has none (RETURN TO HOME is graphite). Everything else is a white button (`Button variant="success"`), a graphite button (`secondary`), or red text on black / `#1C1C1C` (`danger`, `DeleteButton`).
* **Meaning without hue:** status is shown with white / grey / red plus position and pattern, never green or yellow:
  * Stimulus: RECOVERING = white (solid), RECOVERED = grey `#8A8A8A` (dotted), OVERDUE = red (striped), UNLOGGED = `#3A3A3A`.
  * Done sets / DONE ✓ / success = white: a done set's ✓ is a white circle with a black tick (undone = a `#4A4A4A` outlined circle) and the row recedes to `#121212`.
  * Performance chart: one series is always **selected** — by default **DISTANCE TO GOAL** (`GOAL_SERIES_ID`, own chart only): for each date, the tracked lifts' (Big 3 + OHP, `CORE_LIFT_IDS`) goal − latest estimated 1RM, never below 0, added up (`buildGoalDistanceSeries`). Goals come from the STRENGTH CLASS GOAL picker at the top of the page (`getLiftGoalStats` → `getExRxTargetForLift`), so changing the class re-draws the line. Only lifts with a goal and something logged count, and the line starts once each of them has a value. Its row (`GoalDistanceRow`) is first: `DISTANCE TO <CLASS> GOAL` over START | LATEST (DONE ✓ at 0) | CLOSED (start − latest) | REACHED (lifts at their goal, e.g. 2/4); its points carry no asterisk. **Every chart opens on this view, friends' profiles included:** a friend's chart measures distance to *their* strength class goal (`renderProgressPage({ goalSettings })` from `ProfileView`: their `goals.targetStandardClass` / `customGoalWeights` and `bodyweightLbs`; Intermediate if unset; height isn't shared, so yours is used). The selected series is drawn red (2.5 px, white values, its row's title strip red). Tapping a row selects that lift; tapping the selected row goes back to the default. The chart is **framed on the selected series** (its dates and its value range); every other series is drawn grey (`LIFT_LINE_GREY`, 1.5 px) behind it where it falls in the frame, labelled at its end (lift + value); point markers are only drawn inside the frame. The selected lift's stat cells are a step brighter (`SELECTED_STATS_BG` `#242424` in `LiftGoals.jsx`; not `#2A2A2A`, which would drop red TO GO below 4.5:1). **The chart block (time frame, chart, EARLIER / LATER) is sticky:** it sits in the page and pins directly under the locked header (its height measured with a `ResizeObserver`, `stickyTop`) as the lift rows scroll underneath, letting go at the end of the list; a black backing hides rows behind its rounded top corners. **Value labels never overlap:** each label's box is checked, and where two collide only the later point's label is drawn (ties: the selected series).
  * Synced sessions: YOU / @FRIEND are pills (selected = white fill); the explanation line is grey.
  * Messages and banners sit on graphite; their wording and red text carry the meaning (no tinted red / green / yellow boxes).
* **Red text only on black or `#1C1C1C`** (≥ 5:1); on raised graphite `#2A2A2A` it is 4.31:1 and fails, so destructive buttons are transparent with an outline (`Button variant="danger"`, `DeleteButton`) and RESET / the running rest countdown sit on `#1C1C1C`.
* **Secondary buttons are raised graphite `#2A2A2A`** (`UI.secondaryBtnCenter`), so they still read as buttons inside a tile or pop-up (CANCEL).
* **Groups:** `SHARED_GROUP_OUTER` is a rounded (14 px) tile that clips its cells; a group holding an exercise picker uses `SHARED_PICKER_GROUP` (rounded, never clips) so the picker's search list can spill out (the PROGRESS chart + lift rows, the Personal Records add panel while open, the Goals add pop-up, the History filter). * **Readability rules:**
  * **Calculated vs true 1RMs:** a 1RM worked out from a multi-rep set (weight × (1 + reps / 30)) or saved from the 1RM calculator (its PR set gets `estimated: true` unless that weight was actually done for 1 rep) shows with an asterisk (`225*`); one actually lifted for 1 rep shows plain. Helpers in `workoutEngine.js`: `isCalculated1RMSet`, `best1RMInfoOfSets` (`{ value, calculated }`), `oneRepMaxLabel(value, calculated)`, and `calculated` on `getBestHistory1RMInfo` (ties go to the true single). Used by the exercise 1RM box (LAST / NOW / PR), the weight pop-up's 1RM box, Personal Records, the lift rows (START / PR / LATEST) and chart point labels, the 1RM calculator's estimate, leaderboard Big 3 totals (marked if any lift in them is) and OHP, and the Home ticker. A PR typed in through the weight pop-up counts as lifted. The key `* Calculated from your reps, not lifted for 1 rep.` (`CalculatedOneRepMaxKey` in `LiftGoals.jsx`) shows under the Performance lift rows and Personal Records whenever a value there has an asterisk. Not marked: MOST IMPROVED and the 1000 LB CLUB total.
  * Minimum text size **10–11 px** for caps labels and 11 px elsewhere; SVG text renders at ≥ 11 px after the chart scales down (chart text 12.5 in a 360-wide viewBox).
  * WCAG contrast: white on `--cr-red`, black on white; red as text uses `--cr-red-text` (≥ 4.5:1 on black and graphite).
  * Tap targets at least 44 × 44 px (selects fill their whole cell; `DeleteButton` defaults to 44 px; SHOW / HIDE password pills are 44 px). The session header (nav + `SessionTitleBar` + `SessionRestTimerBar`, 40 px rows) is ≈ 146 px at phone width.

The per-exercise filters, exercise lists and search always use the whole library.

A scheme the athlete picks, and loaded routines' schemes, are kept.
* **`LOAD ROUTINE`:** a blank live session (no exercises yet) shows `+ ADD EXERCISE` | `LOAD ROUTINE` side by side; LOAD ROUTINE opens the routine browser (`setRoutineSelectReturnView('session')`), which loads the picked routine back into the session. Once the session has an exercise only `+ ADD EXERCISE` remains.
* **`+ ADD EXERCISE`** (the button under the slots) appends one auto-guessed slot (`handleAddAutoSlot` → `buildGeneratedAutoSlots(slots, { addOne: true })`: the next unfilled `routinePreferences` category, cycling once the routine is full). The exercise is chosen by `pickBest` in `buildGeneratedAutoSlots` (shared with AUTO SESSION): only exercises that fit `selectedGymId` and aren't already in the workout; score = days the muscle group is behind on the stimulus map (`muscleStimulusStatus`, capped at 14, weighted by `MUSCLE_GROUP_WEIGHT` so neck/forearms/calves rank low) + `BIG4_BONUS_DAYS` for the Big 3 + OHP (or their gym equivalents) on Compound picks − a penalty for a muscle group already in the workout; curated (non-`exrx_`) and `isPriority` exercises break ties; stretches/isometrics are skipped. The athlete edits it in place; there is no add-exercise pop-up or `AUTO COMPLETE` button in the editor.
* **Always-Expanded Workout Slots & Grippy Drag Handles:**
  * Slots are never collapsed; exercise and set number badges display **grippy dot patterns** and are the drag handles: hold and drag (touch or mouse, `usePointerReorder`) to reorder; the held row follows the finger and the landing row gets an orange outline.
  * **No text selection / iOS long-press callout** anywhere in the app UI (`.kinetic-app { user-select: none; -webkit-touch-callout: none }` in `KINETIC_CSS`); inputs, textareas and contenteditable keep normal selection. The drag handles also cancel the context menu.
  * Row 1: the exercise name / search box; Row 2: `Type`, `Muscle Group`, `Equipment`; Row 3: `Scheme`, `SETS`, `REPS`. The equipment filter always lists every equipment type in the library (`getAllEquipmentFilterOptions`); picking one the exercise doesn't use switches to the most similar exercise that does, keeping the muscle group whenever possible: same type + same muscle group, then same muscle group in another type, then what the filters show, and only then anywhere (the only case where the muscle group changes; the muscle filter is otherwise left as it was). The rows span the full width; deleting an exercise is the red `DELETE` at the end of its bottom button row.
  * Supersets show the same three rows twice (A, B), each fully independent, with interleaved sets; RECALCULATE and set edits use each half's own scheme. A superset has **3 sets** (`SUPERSET_SET_COUNT`; the scheme's last 3 sets, `trimSetsTo`), and its SETS box is for both exercises (a rebuilt half matches the other half's count). Each set row's name strip reads `SUPERSET <n> · A: <exercise>` / `· B:` — round n is one set of each exercise.
  * Auto-completed and loaded routines populate `muscleGroupFilter` accurately based on the selected exercise.
  * **`Cluster` scheme** (SCHEME menu only, not a type — `CLUSTER_SCHEME` in `workoutEngine.js`): 3 Working sets × 6 reps (`CLUSTER_SET_COUNT` / `CLUSTER_REPS`; SETS / REPS boxes still work), weights from goal progress, and the rest timer runs `CLUSTER_REST_SECONDS` (6 s) after each set while the exercise still has sets left (the usual rest after the last). Not offered for superset halves.
  * Schemes include `3x5`, `3x8`, `3x12` (3 sets; their set types are the last 3 of the first 5 Exercise Set Preferences — Working ×3 by default), `5x5`, `5x6`, `5x8`, `5x10`, `8x8`, `Pyramid`, **`Pyramid 1RM`** (last set is `1 Rep Max`, preceding sets are `Warmup`s ramping from $50\%$ to $85\%$ of 1RM), and `Reverse Pyramid`.
  * **Increment:** the progression increment is added once to the total weight for every exercise (no barbell × 2).
  * **Goal progress (`applyGoalProgressToSets` in `workoutEngine.js`; RECALCULATE, + ADD EXERCISE, AUTO SESSION, routines and swaps via `createWorkoutSlot`, superset halves):** everything goes through ONE **calculated 1RM for the whole exercise** — a set's factor (`getSetOneRepMaxFactor`: rep % `1/(1+(reps−1)/30)` × set-type effort × fatigue for the number of sets, the 1RM calculator's estimate, unrounded) and `getExerciseCalculated1RM(sets)` = the highest weight ÷ factor over the exercise's working (non-warm-up) sets. For rep schemes (`GOAL_PROGRESS_SCHEMES`: 5x5, 5x8, 5x10, 8x8, Pyramid, Reverse Pyramid; not Pyramid 1RM / Timer) on weighted exercises, every non-warm-up set gets the LOWER of (A) last session (`getLastLoggedSetsForExercise`, skips PERSONAL RECORD entries and the workout being edited): when it had the same number of sets and that set's reps + type match, last weight + increment; otherwise last session's calculated 1RM converted to this set + increment, and (B) (`getStored1RM`: best calculated 1RM over all sessions incl. PR entries, or a saved 1RM) + increment, converted to this set. Warm-ups are converted from the 1RM the first working weight implies. Weights round to the nearest min(2.5, increment) lb. The increment is added **once to the total weight** (`getEffectiveIncrementForExercise` no longer doubles barbell lifts). Nothing known yet → the scheme defaults. RECALCULATE: once the first set's weight is entered (typed or done) it stays exactly as entered and the sets before the first working set ramp evenly from it; completed sets and typed weights keep their weight.
  * **Exercise Set Preferences** (`SetPreferencesSection` in `SettingsView.jsx`, Configuration → ROUTINES under ROUTINE PREFERENCES; `settings.setPreferences`, local + cloud, default Warm-up, Warm-up, Working, Working, Working): the type of each set by position for new exercises on 5x5 / 5x8 / 5x10 / 8x8 (`generateSetsForScheme(..., setPreferences)`); the scheme sets the number of sets, positions past the list are Working. Rows: drag handle (`data-set-pref-index`), type dropdown (Warm-up / Working / Top Out / Burn Out), grey ✕ (at least one row), `+ ADD SET`, `RESET TO DEFAULT`.
  * **Per-set locks** (`set.lockType` / `set.lockWeight` / `set.lockReps`, off by default): a small padlock at the LEFT inside every set's type, weight and reps box (6 px from the box's left edge), sharing the box's border and background (`withSetLock` in `SlotEditor`, 20 px `LOCK_COL_PX`, shown when the host passes `onToggleSetLock`; grey open padlock = unlocked, orange closed = locked; `handleToggleSetLock(slotId, exIdx, setId, field)` with field `type` / `weight` / `reps`; Timer sets have no reps lock; all three are per athlete in session sync). Set type, weight and reps are three equal columns (`repeat(3, minmax(0, 1fr))`, ≈ 78 px each at phone width) followed by a 40 px ✓ (52 px without locks); beside the padlocks weights are 13 px and the type dropdown is 11 px with no caret (`no-caret`) so BURN OUT / WORKING fit.
  * **RECALCULATE** (`recalculateSlot(slot, workoutId)`, used by `handleRecalculateSlotWeights` and the REPS box via `reshapeSlot`) rebuilds each exercise from its selections, as if it had just been picked: the scheme's set types and reps (Exercise Set Preferences on the uniform schemes; the REPS box), the current set count (the scheme's last sets; extra sets copy its last one) and weights from goal progress (`applyGoalProgressToSets`). With nothing locked that is the whole result. Then every **locked** value is put back and the rest is worked out around it: a locked weight → the reps it allows (from the calculated 1RM); locked reps → the weight for them; a locked type → its rule from the working set (`setTypeTarget`, the same rule as the type dropdown: e.g. a locked Burn Out = the working weight, 2 more reps). Completed sets are never changed; Timer sets keep their times; band sets keep their colour. Nothing else is held (the old "last edited field" logic and `recalcListRaw` are gone).
  * **Set type change** (`handleUpdateSetType`, rule `setTypeTarget`): re-works that set's weight and reps from the exercise's working set (another Working set of the exercise, else the scheme's working set for that position): Working = the working weight and reps; Warm-up = same reps, lighter (× 0.74 / 0.98); Top Out = same reps, heavier (× 1.04 / 0.98); Burn Out = the working weight, 2 more reps; 1 Rep Max = the calculated 1RM from History, 1 rep (+ the increment on the last set). Locked values stay; Timer sets keep their time; bodyweight exercises keep their weight.
  * **Gym/Equipment Swap (`handleChangeGymSelection`):** Changing the `EQUIPMENT` dropdown in the session/routine editor swaps every slot with no completed sets to its closest equivalent for that equipment (`findEquivalentExerciseForGym`, e.g. Barbell Bench Press → Dumbbell Bench Press). Weights come from the new exercise's history + increment, else the old 1RM converted by `convertEquivalent1RM` (dumbbell ≈ 0.65× barbell), stored on the slot as `estimated1RMs` so repeated swaps don't drift.
  * **Muscle Group Filters:** Muscle group names follow ExRx's body parts, except ExRx's **Waist is called `Core`** (`normalizeMuscleGroupName` maps old saved `Waist` filters; `exercises.csv` says Core). Exercises that train a second body part as much (`SECONDARY_MUSCLE_GROUPS` in `exerciseLibrary.js`, e.g. Barbell / Dumbbell **Thruster** = Thighs + Shoulders) carry `secondaryMuscleGroups`, which `doesExerciseInteractWithMuscleGroup` (muscle filters, stimulus map) also counts. Includes an umbrella **`Legs`** filter matching all lower-body exercises (Thighs, Hips, Calves, Quadriceps, Hamstrings, Glutes, Adductors, Abductors).
* **Locked session header:** the session name, a `DATE` box (live session only, 74 px wide so the `SESSION NAME` label stays on one line even with SYNC showing, `dateValue` / `onChangeDate` on `SessionTitleBar`: the session's `startedAt` as YYYY/MM/DD, typed dates applied on blur), `SYNC` (signed-in, live session only; `SYNC…` while an invite waits, green `SYNCED` once linked), green `SAVE` (reads `FINISH` in a live session, `saveLabel`) and red `RESET` live in the sticky header (`SessionTitleBar`, SAVE/RESET only once the workout has exercises) directly above the rest timer; the editor body has no name or SAVE/RESET rows (the History inline editor, which has no locked header, keeps its name row).
* **Session name pop-up:** the header's SESSION NAME box is a button (the name is cut off with … there); tapping it opens a pop-up (`SessionTitleBar` in `Primitives.jsx`) with the full name in an editable box, CANCEL and red SAVE NAME (Enter saves). Saving goes through `onChangeTitle`, so it counts as a typed name for the auto-namer.
* **Profile photos beside names:** leaderboard rows (`entry.photo`: yours from `profilePhoto`, friends' from their profile), Social search results / incoming / sent requests and friends list, and the Profile FRIENDS tab (yours and a friend's friends). Lists that only carry a username show the photo when that athlete is also your friend, else their initial (`ProfileAvatar`).
* **Session auto-naming** (`withAutoSessionName` / `getSessionMuscleName` in `workoutEngine.js`; `page.js` wraps `setActiveSession` with it, so every change to the live session passes through): a session still called `Session` / `Auto Session` — or one it named itself (`autoNamed`) — is named after the two muscles its exercises train most, from each exercise's main specific muscle (`SESSION_MUSCLE_NAMES`: Pectoralis → Chest, Quadriceps → Quads, Latissimus → Lats…), e.g. Bench + Squat → `Chest and Quads`; ties go to the muscle added first; an auto-named session that becomes empty goes back to `Session`. Typing a name (the title changes while the exercises don't, in an update built from the current session) sets `titleEdited` and stops it; a name set with new exercises (a loaded routine) is kept. A session put back whole from storage isn't mistaken for a rename (the startup restore runs twice in development).
* **RESET** also stops the rest timer and puts it back to the session's default rest (`handleResetSession` in `page.js`). The NEXT line's red dot only shows while a set is waiting.
* **Finishing a session:** the `✓` at the right of the sticky rest-timer bar (`SessionRestTimerBar` `onMarkDone`; grey like an unchecked set until tapped, green while its save confirmation is open via `markDoneActive`) and the header `SAVE` open the save confirmation. After 15 minutes idle a session with completed sets finishes and saves itself (`useIdleAutoFinish`). `NEW SESSION` replaces an empty leftover session so the date is today's; session names no longer include the date (`getDefaultSessionName` = `Session`, AUTO = `Auto Session`, a loaded routine = the routine's name — `formatTitleWithDate` / `stripDateFromTitle` drop an old `YYYY/MM/DD - ` prefix; continuing, saving and syncing a session strip it too, and CSV imports, LOG PAST WORKOUT and PR entries (`<Exercise> PR (N LB)`) are named without a date): the date is `startedAt`, shown in the header's DATE box and in History rows; `formatDateYMD` shows timestamps in local time (never the UTC date).

* Mirrored: exercises added/removed/reordered, exercise/type/muscle/equipment/scheme, sets added/removed/retyped. Each athlete's own numbers are not mixed: weights, reps and checkmarks stay per athlete; each athlete saves their own copy.
* **YOU / @FRIEND tabs on each exercise** (coaching): while synced every exercise in the session has its own two-tab strip above it (`slotTabs` prop of `RoutineEditorView`; which exercises show the friend = `partnerSlotTabs` in `page.js`, slot id → true). YOU is orange; the friend's tab is purple (`PARTNER_TAB_COLOR` `#BF5AF2`, dark text when selected, purple text otherwise) and one purple line at the top of the session explains them (`A purple @x tab shows their numbers; changes there show up on their phone.`, plus the loading note while their numbers load) — no note under each exercise, so the strip costs only ~46 px per exercise. An exercise on the friend's tab shows their numbers — your shared structure with theirs laid over it (`overlaySetValues(activeSession, sessionSync.partnerValues)` = `partnerSession`, built whenever synced) — and is edited by a **second `useWorkoutMutations` copy** (`partnerMutations`: `partnerSession` + `onEditPartnerSession`, so number edits go to the friend via `editPartnerValues` and exercise/set changes also apply to your session with your numbers kept). `RoutineEditorView` picks each exercise's handlers by its tab (`slotHandler`), and the weight / value pop-ups use `routedUpdateSetField` / `routedUpdateSetType` (`isPartnerSlot(slotId)`). Everything else (add / reorder / delete exercises, FINISH, RESET) uses your copy; FINISH and RESET clear the friend tabs. Suggested weights on a friend-tab exercise (RECALCULATE, new sets, LAST / PR) use **their** numbers: while any exercise is on their tab `page.js` loads `fetchAthleteProfileSnapshot` (history, PRs, `settings.goals` → increment and goal type, bodyweight, `settings.setPreferences`; again after 60 s) as `partnerNumbers` and passes them to `partnerMutations` (and `partnerHistory` to the editor). Until they load (or if they can't), yours are used and the note says so. A too-old friend app shows one red line at the top of the session.
* Numbers travel in the row's `structure.values`: `{ [accountId]: { [setId]: { weight, reps, completed, bandColor, durationSeconds, timerStr, lastEditedField, lockWeight, lockReps, at, by } } }` — locks are per athlete too (`collectSetValues`, `sameSetValues`, `mergeValueMaps`, `overlaySetValues` in `sessionSync.js`). Each device stamps its own changed sets with `at` (ms) and pushes them with any edits to the friend's numbers 0.7 s later (`pushNow`: reads the row first, merges per set — the newer `at` wins — keeps the friend's structure unless this device changed it, then writes). Polling applies the friend's structure, their numbers (for the tab) and any of your numbers they edited more recently. No database change was needed.
* Both phones get the tabs and can edit each other's session; it only needs both on the current app. Every write carries `structure.protocol` (`SESSION_SYNC_PROTOCOL` = 2 in `sessionSync.js`); a row the friend wrote without it comes from an older app (no numbers, no tabs, and its saves drop `values`), so `useSessionSync` sets `partnerAppOutdated` and the tabs show a red line asking them to close and reopen the app. `useAppUpdateCheck` makes that rare.
* RESET while synced ends the sync first (it would otherwise empty the partner's session); saving or replacing the session ends it; UNSYNC ends it for both. Invites only reach an open app (no push notifications).
* **Synced workouts in History** (`app/utils/syncedHistory.js`, `app/hooks/useSyncedHistoryUpdates.js`): a session saved while synced (FINISH, idle auto-finish) is tagged `syncedWith: { syncId, partnerId, partnerName }` on the workout and on every exercise (`withSyncInfo`; the exercises are what `workout_history.slots` stores, so the tag reaches the cloud without a new column; `getWorkoutSyncInfo` reads it back). History rows show a purple `SYNCED WITH @x` line. Saving a History edit of a synced workout that **added exercises** (`findAddedSlots`, by slot id) writes them to the sync's `shared_sessions` row as `structure.historyUpdates[myId] = { at, by, byName, workoutDate, slots }` (`postSyncHistoryUpdate`; slots = the shared structure, never weights; the rest of the row is kept). The friend's app checks their rows with updates (`fetchSyncsWithHistoryUpdates`, 4 s after sign-in, every 5 min and on returning to the foreground — only when their History has a synced workout) and, for a synced workout in their History missing those exercises, shows `SyncedHistoryUpdateModal` (`SessionSyncModals.jsx`): `ADD TO MY WORKOUT` (the exercises join their copy via `mergeSessionSyncStructure` — weights from their own history — done and locked, tagged) or `DISMISS`. Either answer is remembered per sync on that device (`yccih_synced_history_acks_v1`). No database change was needed (both athletes can already update the row).

### F. Cloud Sync (`useCloudAndStorageSync.js` + `supabaseAuth.js`)
* **`workout_history` is the source of truth for History.** A new device or iOS home-screen app (which gets its own empty storage) shows only what is in that table.
* **Pull** (sign-in, startup, `RETRY`, app returning to the foreground, network back online; at most every 30s): retries queued deletes, then merges. A workout the ledger marked `synced` that is missing from the server was deleted elsewhere and is removed locally; unconfirmed local workouts are kept and uploaded. Uploads are held until the pull finishes.
* **Push** (debounced after every change): uploads only workouts that are new or changed since confirmed (signature mismatch), in batches of 25; a rejected batch is retried row by row so one bad workout can't block the rest. Returns `{ ok, error, syncedWorkoutIds, failedWorkoutCount }`.
* **Deleting** a History session deletes its `workout_history` row; until that succeeds the id stays queued in the ledger.
* **Never store app state in auth `user_metadata`.** Supabase embeds it in every access token; older builds did (`yccih_cloud_state_v3`), which bloated tokens. `supabase/migrations/2026-11-08_move_metadata_snapshots.sql` moves those workouts into `workout_history` and strips the key, and the `strip_app_state_from_user_metadata` trigger on `auth.users` (also in `supabase_schema.sql`) drops it on every write so outdated clients can't re-add it.
* **An unrecognised token reads as signed-out:** PostgREST answers it with 200 + no rows, not 401. The pull therefore treats a missing own `user_profiles` row as a session error rather than an empty account.
* Failures are never silent: `cloudSyncStatus` (`idle`/`syncing`/`ok`/`error`) drives `CloudSyncBanner`.

### E. Authentication & Beta Access
* Beta sign-up requires the beta tester code: **`imnotcrying`** (case-insensitive). This is only checked in the browser today.
* **Never store passwords.** Sessions are Supabase access + refresh tokens (`yccih_supabase_tokens_v1`); `getValidSupabaseAccessToken` refreshes using the JWT `exp` and never re-sends a password. A rejected refresh token clears the tokens and dispatches `SESSION_EXPIRED_EVENT`, which signs the athlete out on that device (local workout data stays).
* The local account registry (`yccih_registered_accounts_v1`) holds only id/username/email; `purgeLegacyStoredPasswords` deletes passwords saved by older builds at startup. Only offline/dev mode (no Supabase env) keeps a salted SHA-256 hash.
* Sign-out goes through `signOutUser` (revokes the session with Supabase and clears tokens).
* **Delete account** (Profile, next to SIGN OUT, confirmed via `DeleteConfirmModal`): `deleteMyAccount` calls the `delete_my_account` RPC, which deletes the athlete's invites (sent and received), friendships, workout history, routines, profile and `auth.users` row; then `handleDeleteAccount` erases this account's data from the device and resets the app. Any new table holding user data must be added to that function.
* Sign-up with email confirmation enabled does not sign in; the athlete confirms, then signs in. Password resets use the Supabase email recovery link only (its access + refresh tokens sign the athlete in after setting the new password).
