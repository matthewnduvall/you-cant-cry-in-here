# AGENTS.md — Project Context & Rules for "You Can't Cry in Here"

> **Note for coding agents (Claude Code, etc.):** This file contains the complete product, design, architectural, and domain context for *You Can't Cry in Here*. Always follow these rules and target the specific modular files listed in Section 2 when making edits.

---

## 1. Project Overview & Tech Stack
* **App Name:** *You Can't Cry in Here*
* **Framework:** Next.js 16.4+ (App Router, Turbopack, `cacheComponents: true` & `partialPrefetching: true` enabled in `next.config.mjs`).
* **Hosting & Backend:**
  * **Frontend Hosting:** Vercel (linked to GitHub repo `matthewnduvall/you-cant-cry-in-here`).
  * **Database & Auth:** Supabase (`supabase_schema.sql` in repo root defines `user_profiles`, `workout_history`, `routines`, `friendships`, `friend_invites`, `shared_sessions` and `routine_shares` with Row-Level Security, plus the friendship functions/triggers; safe to re-run). One-time data migrations live in `supabase/migrations/`.
  * **Local Persistence:** Update-resilient `localStorage` engine (`yccih_app_state_v3`, Schema Version 3) with debounced 300ms auto-save and `.json` backup export/import.

## 2. Modular File Architecture (Read/Edit Only the Target File)
To keep agent edits fast and focused, views and state hooks are split into dedicated files:

* **App Shell & Header:**
  * `app/page.js` — Top-level state wiring, view router, and modal mounts (~900 lines).
  * `app/components/AppHeaderAndDrawer.jsx` — Sticky top navigation bar (Menu `☰`, title, `FEEDBACK` button; in the session/routine editor also `SessionTitleBar` — session name + green `SAVE` + red `RESET` — and `SessionRestTimerBar` flush beneath it; the header action cells and the rest bar ✓ share `SESSION_ACTION_COL` (58 px) so the orange NEXT bar ends exactly under the SAVE | RESET divider) and slide-out Hamburger Drawer. Header: an orange `←` BACK button just right of ☰ (not on Home), and the app title `YOU CAN'T CRY IN HERE` in the centre ("HERE" in orange): a button to Home on every page. The page's name (`PAGE_TITLES`; none for the live session, whose locked header names it: PERFORMANCE, STIMULUS, SOCIAL, CONFIGURATION, INFO, PROFILE, SESSION…) is not in the header: `PageTitle` (same file, 28 px) shows it at the top of the page itself, under the locked header (`page.js`, every view but Home). BACK = `handleBack` / `goBack` in `page.js`: a real back stack (`backStackRef`) of the places visited since Home (cleared on Home) — a place is a page, plus on the PROGRESS page its tab and a History workout opened from elsewhere (`openHistoryWorkout`, e.g. a chart point, is its own step, so BACK returns to the chart); tab switches on one page are not steps. Each step is also a browser history entry (`pushState` with its depth in `state.yccihBack`, counted in `browserDepthRef`, capped at 30 because browsers keep only ~50 entries), and `popstate` runs the same `goBack`, so the phone's / browser's back gesture matches the ← (`ignorePopsRef` keeps the two in step when places are skipped). A popstate to a deeper entry (browser **forward**) is undone, never treated as back. Reaching Home (by any route) rewinds the browser to where the app started (`rewindToHome`), so back on Home leaves the app instead of stepping through dead entries. Skipped: pages that can't be shown any more (an editor without its draft, a friend profile without a friend, sign-in while signed in, a deleted History workout); empty stack = Home. The menu answers **"where is everything?"**: a quiet grouped index (13 px caps rows, 44 px, no descriptions, grey `›`; the page you're on is a white row with `aria-current`; counts are red pills; SIGN OUT is its one red; the panel scrolls on short phones): `@user` (photo, shown as typed) / `SIGN IN`, then **TRAIN** (New / Current session — `onOpenSession`; Routines with the INBOX count), **TRACK** (Performance, Stimulus), **PEOPLE** (Social with the request count), **SETUP** (Configuration, Info). No HOME row: the title in the header goes home. The footer: signed out its footer reads `NOT SIGNED IN: SAVED ON THIS DEVICE ONLY`; signed in, a red `SIGN OUT` sits at the bottom under `LOGGED IN: <email>` (`onSignOut`). Signed out: a slim grey line under the header (`Not signed in: saved on this device only.` + orange `SIGN IN` + `JOIN`), hidden in the session / routine editor and on the sign-in page.
* **Custom State & Domain Hooks (`app/hooks/`):**
  * `app/hooks/useCloudAndStorageSync.js` — `localStorage` hydration, password recovery hash & email invite URL param detection (`?invite_from=...&beta_code=imnotcrying`), Supabase cloud pull/push, automatic invite-to-friend resolution, and `.json` backup export/import/reset.
  * `app/hooks/useWorkoutMutations.js` — Workout/slot/set creation, auto workout generation (`handleAutoBuildWorkout` for AUTO SESSION, `handleAddAutoSlot` for `+ ADD EXERCISE`), routine loading, drag-and-drop reordering, weight recalculation, saving, and deleting.
  * `app/hooks/usePlateCalculator.js` — Plate & Weight Calculator modal state (plates only; no DIRECT TOTAL mode — tap `TOTAL WEIGHT ✎` to type a number, which re-splits into plates). TOTAL WEIGHT always = bar + plates (× 2 for two sides) + `calcExtraLbs`: the part plates can't make up (e.g. 151.25 lb = 45 + 2 × 52.5 + 1.25) shows as a grey `+1.25 LB OTHER ✕` chip and stays when plates are added or removed, so the total never jumps. A set with no weight opens on the empty bar. Loads (`getLoadSetup`): barbell / trap bar / Smith = 45 lb bar + plates per side; EZ bar = 17 lb bar + plates per side; plate-loaded Lever / Sled = plates per side, no bar; dumbbell, kettlebell, cable / selectorized / machine stacks, landmine and everything else = the picked weights are the total (no bar, no ×2) and handlers for set weights, Personal Records (with optional `prRecordDate` that logs an individual History entry), and custom goal weights.
  * `app/hooks/useSessionSync.js` — Live session sync with a friend: invites (polled every 10 s), accept/decline, pulling the partner's structure every 3 s while synced, pushing own structural edits 0.7 s after they happen (latest edit wins, compared by `updated_at`), each athlete's numbers per set (`structure.values`, see G) with `editPartnerValues` / `partnerValues` for the friend's tab, and ending the sync on UNSYNC / RESET / save. The shared session is marked by `activeSession.syncId` (+ `syncPartnerId`, `syncPartnerName`).
  * `app/hooks/useRoutineShares.js` — Routines sent straight to friends (`public.routine_shares`, migration `supabase/migrations/2026-11-12_routine_shares.sql`): **sending** = a grey `SEND` on your own routines in the routine browser (`RoutinesView` `onSendRoutine`, signed in only) → `SendRoutineModal` (`app/components/RoutineShareModals.jsx`): `@friends` (a copy to every friend, one row each) or one `@friend`, red `SEND TO @FRIENDS` / `SEND TO @X` → `sendTo(friends[])` (`sendRoutineToFriend` per friend; partial failures say so). **Receiving** = checked 4 s after sign-in, every 2 min and on returning to the foreground (`fetchIncomingRoutineShares`, status `pending`) into `incoming`; no pop-up: they wait in the Routines page's **`INBOX`** tab, and their count shows as a red pill (`CountBadge`) on Home's Routines row and the menu's ROUTINES row. Each row: SAVE (`saveShare`: into `savedRoutines` as `received_<id>`, BY @sender), LOAD (`loadShare`, re-worked to your weights; asks `REPLACE YOUR SESSION?` when your session has exercises) or ✕ (`dismissShare`); each answer is written back (`answerRoutineShare`) so it never shows again. RLS: only the two athletes can read a row, only an accepted friend can be sent one (`are_friends`), only the recipient can answer, and a trigger lets an answer change nothing but the status. `delete_my_account` deletes the athlete's rows.
  * `app/hooks/useIdleAutoFinish.js` — 15 minutes without a touch, click or key press (`yccih_last_activity_v1` in localStorage, so a closed or suspended app is checked when it returns; checked every 30 s and on returning to the foreground; activity is recorded at all times, not only during a session, so starting a session — NEW SESSION, LOAD ROUTINE — never inherits the idle time from before it): a live session with at least one completed set is saved to History as it is (`handleAutoFinishActiveSession` in `useWorkoutMutations`: private, not a routine, `autoFinished: true`), closed, and a `SESSION SAVED` notice is shown. A session with nothing completed is left open.
  * `app/hooks/useAppUpdateCheck.js` — keeps open apps on the latest deployment (an iPhone home-screen app left running keeps its old code otherwise, and two synced phones on different versions don't sync numbers). Compares the build baked into the page (`process.env.APP_BUILD_ID`, set in `next.config.mjs` `env` from `VERCEL_GIT_COMMIT_SHA`) with `GET /api/version` (`app/api/version/route.js`, no-store): on returning to the foreground an older build reloads at once (state is already saved on the device); while in use (checks every 5 min and when back online) it shows `UpdateBanner` (`app/components/UpdateBanner.jsx`: `A new version of the app is ready…` + orange `RELOAD`) under the header.
  * `app/hooks/useTelemetryAndAnalytics.js` — Computes `effectiveOneRepMaxes` (highest calculated 1RM from History + manual overrides), `muscleStimulusStatus`, and `progressionSeriesByLift`. `buildProgressionSeriesByLift(history)` is exported (also used for a friend's chart).
  * `app/hooks/usePointerReorder.js` — Drag-to-reorder with pointer events (works with touch, unlike HTML5 drag-and-drop): `handleProps(key)` on each row's `DragNumberBadge` (which passes extra props through), the row attribute on each row, and `rowDragStyle(key)` in each row's style — the held row lifts and follows the finger (translateY + shadow + orange outline) and the landing row gets an orange `outline` (not an inset box-shadow, which the row's own filled cells cover); dragging back over the row's own place cancels the move; **not too sensitive**: the row only lifts after the finger moves 10 px (`LIFT_THRESHOLD_PX`) and only lands on another row once the finger passes that row's middle; rows are found by element within the held row's own list (keys like `0:0` repeat in every exercise, so never `querySelector` by key), and the latest drag state is kept in a ref so release never uses a stale position; options `attribute` (separate ones for nested lists), `canDrop`, and `edgeTop` / `edgeBottom` (holding near the screen edge auto-scrolls on a 16 ms timer, so rows can be dragged past off-screen ones; `edgeTop` clears the sticky session header). Used by ROUTINE PREFERENCES (`data-reorder-index`), exercises in `RoutineEditorView` (`data-slot-reorder`, handle props passed to SlotEditor as `dragHandleProps`) and sets in `SlotEditor` (`data-set-reorder="exIdx:setIdx"`; superset sets only move within their own exercise). No HTML5 drag-and-drop anywhere (it doesn't work with touch).

## 3. Critical Next.js 16 & Environment Rules
1. **No Unstable `Date.now()` in Client Prerender:** Because Next.js 16 `cacheComponents` is enabled, **never** call `Date.now()` directly inside a `useMemo` or top-level render body of a `'use client'` component. Always read `Date.now()` inside a `useEffect` (e.g., `stimulusNowMs`) or event handler.
2. **Verifying Changes:** Run `npm run lint` after edits. `npm run build` is the full check (it surfaces prerender errors like the `Date.now()` rule above). If a sandboxed terminal blocks Turbopack worker sockets on Windows, ask the user to run the command in their own PowerShell window instead.

* **Readability rules:**

### B. Routine Editor & Workout Slots (`RoutineEditorView.jsx`)
* **No top action row (for now):** the `EQUIPMENT` selector and `ROUTINES / LOAD` button are hidden from the session/routine editor.
* **Starting 1RM for an exercise never logged** (`app/utils/starting1RM.js`, `getStarting1RM` / `getStarting1RMInfo`): (1) a related lift you have logged — same Big 3 / OHP family by name (`getLiftFamilyParent`: deadlift / RDL / Romanian / good morning → deadlift; squat → back squat; overhead / shoulder / military / push press → OHP; bench / floor / chest press → bench) — converted by the two lifts' strength standards at the same class (the best such conversion); else (2) the strength standard (`getExRxTargetForLift`) **one class below the goal** (`getStartingClass`: Intermediate → Novice; 1000 LB Club / Custom → Novice) for your bodyweight and height. Used by programs (`getCycleTarget1RM`) and everywhere in `useWorkoutMutations` (its `getHistoricalCalculated1RM` and `createWorkoutSlot` wrap the engine's so new / never-logged exercises start there instead of the library default; `targetStandardClass` and `heightInches` come from `page.js`). The per-exercise filters, exercise lists and search always use the whole library.

A scheme the athlete picks, and loaded routines' schemes, are kept.
* **`LOAD ROUTINE`:** a blank live session (no exercises yet) shows `+ ADD EXERCISE` | `LOAD ROUTINE` side by side; LOAD ROUTINE opens the routine browser (`setRoutineSelectReturnView('session')`), which loads the picked routine back into the session. * **Always-Expanded Workout Slots & Grippy Drag Handles:**

* **History .csv import** (`IMPORT ↑`): the app's `Date,Exercise,Set,Weight,Reps` (or without Set), or **a Fitbod export** as it is — recognised by its header (`Weight(kg)` / `isWarmup`): kg → lb (nearest ¼ lb), `isWarmup` → Warm-up sets, a set with only a `Duration(s)` → a timed set; quoted fields with commas are read properly. Names go through `resolveCsvExercise` (aliases).
* **History Section:**
  * Displays the **last 10 sessions** initially, with a **`SEE ALL (<TOTAL>)`** button at the bottom that paginates in pages of **100**.
  * Each History row has an expand indicator (`+` / `−`) and an outline **red ✕ delete button** (`type: 'history_workout'`) next to it.
  * **History entries are done and locked by default** (`lockAndCompleteSets` in `workoutEngine.js`): FINISH and idle auto-finish log **only the sets marked done** (`keepCompletedSets`: exercises with none are left out; nothing done = nothing logged, the session just closes); a workout entering History (FINISH, idle auto-finish, LOG PAST WORKOUT, PR entries) has every set marked done and its type, weight and reps locked (a lock already turned off stays off). Older entries get the same when shown or edited (`asHistoricalWorkout`, used by `buildHistoryWorkoutEditorProps` and the History branch of `useWorkoutMutations`). It happens once per exercise — the slot is marked `historyLocked` (slots sync with the workout) — so later edits in the History editor, e.g. unticking a set or unlocking a value, are kept.
  * Expanding a History entry renders the full `RoutineEditorView` inline (with no side gutter of its own, `sideGutter`, since the History list already has one — so set rows keep full width and set types aren't cut off). Edits go to a draft (`historyEditDraft` in `page.js`, read and written by `useWorkoutMutations` while that workout is open) and History only changes on **SAVE**: the row at the top of the editor shows `UNSAVED CHANGES` + red `DISCARD` + green `SAVE` (grey and disabled with no edits: `EDITS SAVE WHEN YOU TAP SAVE`); SAVE opens the same save pop-up as FINISH and writes the draft (name, date, exercises, sets) over the logged workout. `HistoricalEditConfirmModal` is no longer triggered by edits.

### D. Social Invites, Friend Profiles & Feedback
* **Friendships (single source of truth: `public.friendships`):**
  * A friend is an `accepted` friendships row (either direction) keyed by Supabase account ids. RLS lets an athlete read a profile, workout history, or shared routines only if they own it or are accepted friends with the owner (`are_friends`). Never add another friendship source (local stores, settings lists, name matching).
  * Removing a friend (`REMOVE FRIEND ✕` under the name on their profile, `handleRemoveFriendClick` in `ProfileView`, confirmed via `DeleteConfirmModal`, then back to Social; the Social friends list has no ✕) deletes the row, which revokes access **both ways**; the other athlete's app drops the cached friend on its next sync (`applyFriendshipSync`), and an open friend profile shows `PROFILE UNAVAILABLE`.
  * Requests: search → `+ ADD FRIEND` inserts a `pending` row; only the recipient can accept (UPDATE policy) or decline (`✕`, deletes the row). Requesting someone who already requested you accepts theirs.
  * Search (`search_athletes` RPC, signed-in only): partial username or exact email; returns id + username only (never emails or stats).
  * Default friend: a database trigger (`handle_new_profile_friendships`) makes every new account friends with `@matt` — found by `default_friend_id()` via the sign-in account email matthew.n.duvall@gmail.com in `auth.users`, falling back to username `matt` — and with anyone who emailed an invite to that address. Nothing re-adds a removed friend.
  * Match friend records with `isSameFriend` (account id only). The local `friendsList` is just a cache of the server list and is cleared on sign-out.
* **Email Invites (`SocialView.jsx` → `/api/invite`):**
  * The inviter must be signed in; the route verifies their Supabase session and records `friend_invites` as them (`record_friend_invite` RPC, else a direct insert under RLS `inviter_user_id = auth.uid()`; the email still goes out if recording fails), then emails the beta code **`imnotcrying`** and a join link (`/?invite_from=<username>&invited_email=<target>&beta_code=imnotcrying`).
  * The join link also carries `invite_id`. The app keeps it (`yccih_pending_inviter_v1`) until signed in, and the next friendship sync calls `claim_invite_link(invite)`: whoever joins through the link becomes friends with the inviter **whatever email they use**; each unused invite can be claimed once. Email matching still works too: new accounts via the trigger above, existing accounts via `claim_my_invites`. Migration: `supabase/migrations/2026-11-09_invite_links_default_friend.sql`.
* **Share stats with friends** (`settings.social.shareStatsWithFriends`, default on): off = friends' apps drop that athlete's history and PRs (`buildAthleteFromProfileRow`: `statsShared: false`, `history: []`), so they leave the profile chart, leaderboards and ticker; a synced session's friend tab then uses your numbers. Like bodyweight, the rows are still readable under RLS.
* **Share bodyweight with friends** (Social → PRIVACY, `settings.social.shareBodyweightWithFriends`, synced; **off unless the athlete turns it on**, including accounts saved before it existed): friends' apps only read a bodyweight when it is on (`buildAthleteFromProfileRow` returns `bodyweightLbs: null` otherwise). **The leaderboards rank everyone anyway**: `rankingBodyweightLbs` (the saved bodyweight, shared or not) is used only for the BW ratios and standings (`rankingBwOf` in `LeaderboardView`), and no board shows a bodyweight (rows read `N LB • STANDING`); only friends with no bodyweight saved sit out the BW boards (a sentence under the tabs says how many). Their chart's goal maths and a synced session's suggested weights use your bodyweight instead. The number itself is still in `user_profiles.settings`, which friends can read under RLS, so this hides it in the app rather than on the server.
* **Public/private profiles:** `settings.social.profileIsPublic` (default true, synced in `user_profiles.settings`; set on the Social page → PRIVACY & SHARING). The `friends_of_athlete(target)` RPC lists a friend's friends only while you are friends with them and they are public, includes only public athletes (never you), and returns your relation to each (`friends`/`requested`/`incoming`/`none`).
* **Friend Profiles (`ProfileView.jsx`):**
  * Never display a friend's email address—only display `@<username>`.
  * PRs load from the friend's `workout_history` by account id (`fetchAthleteProfileSnapshot`); RLS returns nothing once the friendship is removed. **PRs come only from logged History** (`buildHistoryPRs` in `workoutEngine.js` — the one History scanner, also used by the friend snapshot, profile PRs, the leaderboard and the Home ticker): 1RM numbers saved in settings / `one_rep_maxes` (old imports, removed workouts) are never shown as PRs, so an exercise with no data has no PR (TBD / 0). At the source too: the saved / uploaded `oneRepMaxes` are exactly `buildHistoryPRs(history)`, suggested weights get `effectiveOneRepMaxes` (History-based), and CSV import, the weight pop-up's PR mode and the 1RM calculator no longer write separate 1RM numbers (their History entries are the record).
* **Footer:** Every view renders `Copyright © 2026 MaNoDuV LLC` at the bottom of the app column (`app/page.js`).
* **Feedback Delivery (`FeedbackModal` & `app/api/feedback/route.js`):**
  * Prompts `ENTER YOUR FEEDBACK BELOW. IT WILL BE AUTOMATICALLY SENT WITH DIAGNOSTIC LOGS FROM THIS SESSION (<N> LOG EVENTS).`
  * Sends only via `/api/feedback` (the server tries Resend, then FormSubmit). The browser never posts to FormSubmit itself (that duplicated feedback).

### G. Live Session Sync (`useSessionSync.js`, `sessionSync.js`, `public.shared_sessions`)
* One `shared_sessions` row per sync (owner, participant, status `pending`/`accepted`/`declined`/`ended`, `structure` JSONB). RLS: only the two athletes can read/update/delete; only an accepted friend can be invited (`are_friends`); a trigger stops the athletes being swapped. Migration: `supabase/migrations/2026-11-09_shared_sessions.sql`; `delete_my_account` deletes the athlete's rows.
* Mirrored: exercises added/removed/reordered, exercise/type/muscle/equipment/scheme, sets added/removed/retyped. Each athlete's own numbers are not mixed: weights, reps and checkmarks stay per athlete; each athlete saves their own copy.
* **YOU / @FRIEND tabs on each exercise** (coaching): while synced every exercise in the session has its own two-tab strip above it (`slotTabs` prop of `RoutineEditorView`; which exercises show the friend = `partnerSlotTabs` in `page.js`, slot id → true). YOU is orange; the friend's tab is purple (`PARTNER_TAB_COLOR` `#BF5AF2`, dark text when selected, purple text otherwise) and one purple line at the top of the session explains them (`A purple @x tab shows their numbers; changes there show up on their phone.`, plus the loading note while their numbers load) — no note under each exercise, so the strip costs only ~46 px per exercise. An exercise on the friend's tab shows their numbers — your shared structure with theirs laid over it (`overlaySetValues(activeSession, sessionSync.partnerValues)` = `partnerSession`, built whenever synced) — and is edited by a **second `useWorkoutMutations` copy** (`partnerMutations`: `partnerSession` + `onEditPartnerSession`, so number edits go to the friend via `editPartnerValues` and exercise/set changes also apply to your session with your numbers kept). `RoutineEditorView` picks each exercise's handlers by its tab (`slotHandler`), and the weight / value pop-ups use `routedUpdateSetField` / `routedUpdateSetType` (`isPartnerSlot(slotId)`). Everything else (add / reorder / delete exercises, FINISH, RESET) uses your copy; FINISH and RESET clear the friend tabs. Suggested weights on a friend-tab exercise (RECALCULATE, new sets, LAST / PR) use **their** numbers: while any exercise is on their tab `page.js` loads `fetchAthleteProfileSnapshot` (history, PRs, `settings.goals` → increment and goal type, bodyweight, `settings.setPreferences`; again after 60 s) as `partnerNumbers` and passes them to `partnerMutations` (and `partnerHistory` to the editor). Until they load (or if they can't), yours are used and the note says so. A too-old friend app shows one red line at the top of the session.
* Numbers travel in the row's `structure.values`: `{ [accountId]: { [setId]: { weight, reps, completed, bandColor, durationSeconds, timerStr, lastEditedField, lockWeight, lockReps, at, by } } }` — locks are per athlete too (`collectSetValues`, `sameSetValues`, `mergeValueMaps`, `overlaySetValues` in `sessionSync.js`). Each device stamps its own changed sets with `at` (ms) and pushes them with any edits to the friend's numbers 0.7 s later (`pushNow`: reads the row first, merges per set — the newer `at` wins — keeps the friend's structure unless this device changed it, then writes). Polling applies the friend's structure, their numbers (for the tab) and any of your numbers they edited more recently. No database change was needed.
* Both phones get the tabs and can edit each other's session; it only needs both on the current app. Every write carries `structure.protocol` (`SESSION_SYNC_PROTOCOL` = 2 in `sessionSync.js`); a row the friend wrote without it comes from an older app (no numbers, no tabs, and its saves drop `values`), so `useSessionSync` sets `partnerAppOutdated` and the tabs show a red line asking them to close and reopen the app. `useAppUpdateCheck` makes that rare.
* RESET while synced ends the sync first (it would otherwise empty the partner's session); saving or replacing the session ends it; UNSYNC ends it for both. Invites only reach an open app (no push notifications).
* **Synced workouts in History** (`app/utils/syncedHistory.js`, `app/hooks/useSyncedHistoryUpdates.js`): a session saved while synced (FINISH, idle auto-finish) is tagged `syncedWith: { syncId, partnerId, partnerName }` on the workout and on every exercise (`withSyncInfo`; the exercises are what `workout_history.slots` stores, so the tag reaches the cloud without a new column; `getWorkoutSyncInfo` reads it back). History rows show a purple `SYNCED WITH @x` line. Saving a History edit of a synced workout that **added exercises** (`findAddedSlots`, by slot id) writes them to the sync's `shared_sessions` row as `structure.historyUpdates[myId] = { at, by, byName, workoutDate, slots }` (`postSyncHistoryUpdate`; slots = the shared structure, never weights; the rest of the row is kept). The friend's app checks their rows with updates (`fetchSyncsWithHistoryUpdates`, 4 s after sign-in, every 5 min and on returning to the foreground — only when their History has a synced workout) and, for a synced workout in their History missing those exercises, shows `SyncedHistoryUpdateModal` (`SessionSyncModals.jsx`): `ADD TO MY WORKOUT` (the exercises join their copy via `mergeSessionSyncStructure` — weights from their own history — done and locked, tagged) or `DISMISS`. Either answer is remembered per sync on that device (`yccih_synced_history_acks_v1`). No database change was needed (both athletes can already update the row).

### F. Cloud Sync (`useCloudAndStorageSync.js` + `supabaseAuth.js`)
* **`workout_history` is the source of truth for History.** A new device or iOS home-screen app (which gets its own empty storage) shows only what is in that table.
* **Pull** (sign-in, startup, `RETRY`, app returning to the foreground, network back online; at most every 30s): retries queued deletes, then merges. A workout the ledger marked `synced` that is missing from the server was deleted elsewhere and is removed locally; unconfirmed local workouts are kept and uploaded. Uploads are held until the pull finishes.
* **Push** (debounced after every change): uploads only workouts that are new or changed since confirmed (signature mismatch), in batches of 25; a rejected batch is retried row by row so one bad workout can't block the rest. Returns `{ ok, error, syncedWorkoutIds, failedWorkoutCount }`.
* **Deleting** a History session deletes its `workout_history` row; until that succeeds the id stays queued in the ledger.
* **Never store app state in auth `user_metadata`.** Supabase embeds it in every access token; older builds did (`yccih_cloud_state_v3`), which bloated tokens. `supabase/migrations/2026-11-08_move_metadata_snapshots.sql` moves those workouts into `workout_history` and strips the key, and the `strip_app_state_from_user_metadata` trigger on `auth.users` (also in `supabase_schema.sql`) drops it on every write so outdated clients can't re-add it.
* **An unrecognised token reads as signed-out:** PostgREST answers it with 200 + no rows, not 401. The pull therefore treats a missing own `user_profiles` row as a session error rather than an empty account.
* **One account's data per device:** the workouts / routines on a device belong to the account signed in when they were saved (`yccih_data_owner_v1`, set on every sign-in pull). Signing in as a different account removes the previous account's workouts and routines (the ids recorded while it was signed in, `yccih_owner_items_v1`; everything when there is no record) and resets every per-account setting to its default (`resetAccountSettings`: bodyweight / height, goals, equipment, program, privacy, profile photo, 1RMs, friends cache) before the new account's own come down — nothing of theirs is uploaded to the new one. Workouts logged while signed out after that account signed out aren't in its record, so they stay and are uploaded to the account that signs in.
* **Rows owned by another account:** `workout_history.id` and `routines.key` are global primary keys, so uploading a row whose id / key another account owns is refused by RLS (403, "new row violates row-level security policy (USING expression)" — only that exact message counts; any other 403, e.g. "permission denied", stays an ordinary error and never removes data). `pushCloudStateForUser` retries routines one by one like History, returns those rows as `foreignWorkoutIds` / `foreignRoutineKeys` instead of errors, and `useCloudAndStorageSync` removes them from the device (`console.warn`). This also cleans devices that switched accounts before the owner check existed (and the profile's `recentHistory` copy on the next push).
* Failures are never silent: `cloudSyncStatus` (`idle`/`syncing`/`ok`/`error`) drives `CloudSyncBanner`.

### E. Authentication & Beta Access
* Beta sign-up requires the beta tester code: **`imnotcrying`** (case-insensitive). This is only checked in the browser today.
* **Never store passwords.** Sessions are Supabase access + refresh tokens (`yccih_supabase_tokens_v1`); `getValidSupabaseAccessToken` refreshes using the JWT `exp` and never re-sends a password. A rejected refresh token clears the tokens and dispatches `SESSION_EXPIRED_EVENT`, which signs the athlete out on that device (local workout data stays).
* The local account registry (`yccih_registered_accounts_v1`) holds only id/username/email; `purgeLegacyStoredPasswords` deletes passwords saved by older builds at startup. Only offline/dev mode (no Supabase env) keeps a salted SHA-256 hash.
* Sign-out goes through `signOutUser` (revokes the session with Supabase and clears tokens).
* **Delete account** (Profile, next to SIGN OUT, confirmed via `DeleteConfirmModal`): `deleteMyAccount` calls the `delete_my_account` RPC, which deletes the athlete's invites (sent and received), friendships, workout history, routines, profile and `auth.users` row; then `handleDeleteAccount` erases this account's data from the device and resets the app. Any new table holding user data must be added to that function.
* Sign-up with email confirmation enabled does not sign in; the athlete confirms, then signs in. Password resets use the Supabase email recovery link only (its access + refresh tokens sign the athlete in after setting the new password).
